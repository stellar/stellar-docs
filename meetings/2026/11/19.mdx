## Meet Stellar Go CLI

This week's topic was [Stellar Go CLI](https://github.com/stellar-go-cli/stellar-go-cli), an open-source CLI for Stellar, written in Go. In one binary, it covers wallets, payments, swaps, SEP-41 assets, W3C DIDs and Verifiable Credentials, a pure-Go Soroban RPC client, and an MCP server for AI agents. Follow the project even if you are not a Go developer. Also, hello to the Scopuly team in the chat.

Stellar Go CLI is a community project. Its README says: "This is not a Stellar Development Foundation project."

## Olvis and the Origin of the Project

My guest was **Olvis Gil Ríos**, founder of **OG Technologies EU**. Olvis has been in the Stellar community for about eight years. His first Stellar project was a peer-to-peer travel platform. He also works on MozartPay, and one MozartPay product is [Orchestrated Agreements](https://github.com/mozartpay/OAs).

The CLI started inside that product. Olvis wanted the community to use it, and feedback told him to open-source it in its own repository. He did that. Orchestrated Agreements is now its first downstream user.

The gap he saw: the ecosystem had no unified, pure-Go CLI. His target users are Go developers who deploy Soroban contracts, make payments, and do swaps. For enterprises, the angle is ISO 20022 reporting. So far the MCP server has the most traction, because it lets agents use the CLI. Olvis wants feedback and contributors.

Stellar has a Go SDK, the [go-stellar-sdk](https://github.com/stellar/go-stellar-sdk). To my knowledge, Stellar had no Go CLI for Go developers until now. Open issues and leave comments on the repo. I also encouraged Olvis to apply to Drips Network as a maintainer.

## What Stellar Go CLI Is

Install it with Homebrew or `go install`:

```bash
brew install stellar-go-cli/tap/stellar-go-cli
# or
go install github.com/stellar-go-cli/stellar-go-cli/cmd/stellar-go-cli@latest
```

OG Technologies EU is an IT consulting and software development firm in Vienna, Austria. It works on MiCA-ready payments, tokenization, and digital identity, for PSPs, EMIs, crypto asset service providers, and issuers. The skills on Olvis's slide: Stellar and Soroban engineering, ISO 20022, the EUDI wallet, W3C standards, and DORA readiness.

What the CLI gives you:

- Wallets, payments, swaps, and SEP-41 assets, all natively in Go.
- W3C Verifiable Credentials and ISO 20022.
- A pure-Go Soroban RPC client.
- An MCP server that exposes these capabilities to AI assistants and agents.
- Private keys stored apart from the agent, which lowers the risk that an agent mismanages keys.

The facts from the slide: it needs Go 1.26 or later, it is Apache 2.0 licensed, and it works on mainnet and testnet. The latest version is 0.8.0. Olvis said it is "pretty close to version one".

## Architecture

The CLI is modular and package-based. You can import one package into your own Go service. You do not need to adopt the whole CLI. The repository is a Go workspace with reusable packages, a CLI entry point, an MCP server, and signed container images.

The packages under `pkg/` ([pkg.go.dev](https://pkg.go.dev/github.com/stellar-go-cli/stellar-go-cli)):

- `soroban`: a pure-Go Soroban RPC client. Upload Wasm, deploy, invoke, simulate, and query events.
- `iso20022`: ISO 20022 XML generation, validated against the official XSDs.
- `vc`: DID creation, and Verifiable Credential issuance and verification.
- `swap`: Stellar DEX path payments. Quote, then execute.
- `x402`: the x402 pay-per-use protocol.
- `models`: shared types, such as payments, assets, and DID documents.
- `crypto`: key generation, hashing, and encoding.

The CLI has more than 14 command groups. The MCP server exposes CLI tools to AI agents over stdio or SSE.

## ISO 20022 for Enterprises

The goal is to make it easier to integrate banks, financial services, and large institutions, for example for payroll and cross-border payments. Olvis described it as a bridge between the Stellar network and the current financial system. Batch disbursement is an important case.

The message types the README lists:

- `pacs.008`: customer credit transfer.
- `pacs.002`: payment status report.
- `pacs.004`: payment return.
- `pacs.009`: financial institution credit transfer.
- `pain.001`: payment initiation, for batch disbursements.
- `pain.002`: payment initiation status report.
- `camt.053`: account statement.
- `camt.054`: settlement notification.

## Release 0.8.0 and the Security Assessment

Release 0.8.0 is about the **custodian signer daemon**:

- Key custody moves behind a Unix socket.
- A granular permission policy applies to each operation.
- MCP agents and downstream services request a signature through a controlled interface. They do not hold raw seeds.
- It is the groundwork for separated key custody in production deployments.

This work came out of a security assessment by Runtime Verification, dated October 13, 2026. The release also added an end-to-end test suite and differential fuzzing. The fuzzing compares the Go CLI with the official Stellar CLI, which is written in Rust. Olvis said the results did not lean to one side.

For Olvis, any developer or user must be able to use an open-source public tool safely. The specs, the verification roadmaps, and the signed release artifacts are all in the repository. Start with the [security assessment documents](https://github.com/stellar-go-cli/stellar-go-cli/tree/main/docs/audit) and the [signer architecture](https://github.com/stellar-go-cli/stellar-go-cli/blob/main/docs/audit/mcp-signer-architecture.md).

## Use Cases

- **Agentic payments.** The MCP server is for users and developers who work with AI agents. Olvis said OrbitLens called the CLI a "Swiss knife tool for AI agents".
- **ISO 20022 for enterprises and NGOs.** NGOs can use it for humanitarian transfers. Enterprises and NGOs often give a `pain.001` and the bank confirmation to the bank, the donor, or the auditor, and today they do this by hand. The `iso20022` package turns Stellar payments into ISO 20022 XML that validates against the official XSDs.
- **Builder integrations.** Use it as one scriptable Go binary, or embed the packages in Go services. Olvis named the [Stellar Disbursement Platform](/docs/platforms/stellar-disbursement-platform) and the Stellar [wallet backend](https://github.com/stellar/wallet-backend) as Go-based services where it fits.

## Live Demo

Olvis ran the guided demo script from the repository, [`scripts/demo.sh`](https://github.com/stellar-go-cli/stellar-go-cli/blob/main/scripts/demo.sh). It runs in a throwaway sandbox and has seven sections:

1. **DID and Verifiable Credential, offline.** `did create` makes a DID document and stores it locally. `did attest` issues a KYC credential, here with the `did:ebsi` method. `did verify` checks the credential, and `did show` prints the DID and its method.
2. **Configuration and system status.** `init` writes the config for the Stellar testnet. `status` showed the DID as linked and no wallet connected yet. Olvis also listed the current integrations.
3. **Testnet wallet.** The CLI creates a keypair, funds it with Friendbot, and shows the new balance and the link to the DID. The linked DID can carry any type of attestation. EBSI is only the example.
4. **Payment.** `pay send` sent 1 XLM on testnet.
5. **DEX path payment quote.** A read-only `swap quote` returns the quote and its details.
6. **Compliance report.** An ISO 20022 export of the transaction.
7. **Soroban contract.** Deploy and simulate on testnet, in pure Go.

The CLI has many more features than the demo showed. For the exact commands and flags, read the [Quick Start](https://github.com/stellar-go-cli/stellar-go-cli#quick-start) in the README.

## Q&A With Olvis

- **Will it keep up with the Stellar CLI?** I think it is great to see a builder make a more niche tool for Go developers and enterprise use. Stellar Go CLI is not the same tool in Go: it has many more features. But SDF engineers update the Stellar CLI often. Version 30, for example, added the `stellar token` admin commands and muxed contract addresses. Olvis: more tools are better, because "in diversity there is strength". Keeping up with the Stellar CLI is important, and that is why the team runs differential fuzzing against it. He also wants to use what Go offers to go beyond the current capabilities. An open-source project can open issues or bounties for feature parity. Matias added in the chat that it must have at least feature parity with the official tools.
- **Why Go, and why not plugins for the official CLI?** Matias asked this one. Olvis: Go gives a robust, efficient, and fast way to build software. Many important ecosystem and SDF repositories are in Go, such as the wallet backend and the Stellar Disbursement Platform. The ecosystem has few Go tools, and more Go tooling helps the developers who build Go services. A comparison of the two CLIs could help builders decide.
- **Are the demo credentials real KYC?** I saw "KYC level 2" in the demo and asked if the credential was self-issued, and if you can configure an external issuer. Olvis: self-issued credentials are not KYC, because anyone can claim "I did my own KYC". The right way is an external issuer, and you can configure one. The README is clear here. Credentials are self-issued unless you configure an external issuer, and the `did:ebsi` identifiers are never registered on EBSI, so they prove key control, not identity. Enterprises want to configure their own issuers, so this matters for enterprise use.
